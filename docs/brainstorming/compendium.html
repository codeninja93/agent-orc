Part I

The Spine

Five findings that require all three sessions to see. Each one is an agreement between lenses that never spoke to each other.

Finding One · The headline

Three independent convergences

Two unrelated routes arriving at the same mechanism is the strongest evidence a brainstorm can produce. It happened three times across these sessions — twice inside a single day’s lenses, once across two sessions that were about different subjects entirely.

A single lens can talk itself into anything. That is the known failure of structured ideation: pick a metaphor and the metaphor will obligingly produce a system. The defence is triangulation — and triangulation is not something you can plan for, only notice afterwards. These three convergences were noticed afterwards.

In each case the two routes had no shared vocabulary, no shared source material and, in the third case, no shared session. What they share is an answer.

Convergence C deserves a second look, because it is the one that cost something. Session two was commissioned to design the memory layer — its stated goal was to turn the orchestrator “from a task runner into a factory that compounds.” Seventy-nine ideas later it concluded that the correct amount of memory to build first is none, and that most of the rest is a query against git (S2·042). A session that argues itself out of its own subject is the least likely kind of motivated reasoning there is.

Two fields converging is a strong signal it is correct. Session 2 · Cross-Pollination · S2·039

The practical use of this finding is prioritisation. Of the 292 ideas in this volume, three carry independent corroboration. Those three — spec echo, log-then-consolidate, and no-memory-in-v0 — are the ones to build against first, and session three says as much about the first of them: load-bearing, so build it first.

Finding Two · An arc across all three sessions

Tokens, then context, then attention

Deep arrived wanting token-minimal subagents. By the end of the day the premise had been inverted: the expensive resource is not tokens at all, and the system should spend compute lavishly to protect the thing that actually costs.

This is the only thread that needs all three sessions to complete. Session one attacked the premise twice and did not finish the job; session three finished it from a direction session one could not have taken, because it required asking what a question costs the human rather than what an answer costs the budget.

Downstream of the inversion, a set of ideas that looked like separate features turn out to be one policy. Question compression — the Interviewer’s real job, named in S1·003 — is compute spent to avoid attention. The interrupt budget (S1·001) and the escalation auction (S1·002) price attention explicitly. Answer-from-repo-first with a tracked deflection rate (S1·027, S3·019) spends retrieval to avoid a question. Speculative parallel execution (S1·020) spends three executors because “compute is cheap, Deep time is not” — written in session one, justified properly only in session three.

And the true-north metric falls out of it directly: the percentage of features completed with zero mid-flight interruptions (S3·081), which is the engineering form of the secret wish in the same lens — describe a feature, go make coffee.

Finding Three · A recurring axis

Reversibility, not trust

One idea surfaced three times, in three lenses, wearing three different costumes: as a contradiction dissolved, as a defence against trust collapse, and as something the human must be able to see.

The autonomy question — how much should the system be allowed to do without asking — is unanswerable as stated, because it is phrased as a question about trust. Trust is a feeling and cannot be engineered. Rephrase the variable as reversibility and the whole problem becomes a property of the action, not of the relationship.

The engineering consequence is specific and cheap. Nearly every guard in the archives is a reversibility guard in disguise: the three-tier isolation ladder (S1·048), no push rights in the executor container (S1·095), protected branches as the last barrier (S1·096), PR by default rather than direct commit (S3·077) and the undo command whose mere existence is what makes delegation feel safe (S3·046). None of these require deciding how much the system is trusted.

Finding Four · The repeated verdict

The answer kept being: don’t build it yet

Across fourteen lenses and 292 ideas, the recommendations that survived scrutiny were overwhelmingly subtractive — and the reason is named in session one and confessed in session three.

Session one identified fifteen predators stalking the system and then named the biggest one, which is not a technical failure at all: maintenance burden — the orchestrator eating the very time it was built to save (S1·099). Session three found the same predator from the inside, as a feeling: building the orchestrator is more fun than building the products (S3·075).

Those two entries are the same finding at different altitudes — one an architectural risk register, one an honest admission under a shadow-work lens. Together they explain why almost every conclusion in this volume is a refusal.

Two counter-metrics were proposed to keep the restraint honest, one per session. Session two: measure memory ROI as retrieval token cost against measured reduction in rework, and delete the memory layer outright if that number is not positive (S2·079). Session three: the real success metric is shipping velocity of actual products, never sophistication of the tool (S3·075). Both are instruments for catching the same failure before it has eaten a quarter.

The biggest real predator is maintenance burden — the orchestrator eating the very time it was built to save. Session 1 · Predator and Prey · S1·099
Finding Five · The joint conclusion

Shadow mode is an interface product, so the interface is v0

This is the one conclusion no single session reached. It needs session one’s build order, session two’s refusal to add memory to it, and session three’s observation about what shadow mode actually is.

Session one ended with a build order that put the interface late: event log and git-as-bus, then a deterministic engine with three agents, then a TUI on the event stream, then shadow mode to measure, then earned autonomy. Read as a stack, the human-facing layer sits near the top — which is the conventional order and, on these three logs, the wrong one.

One further consequence, from session three’s synthesis: the silence-means-success contract — arrived at independently by three separate metaphors — is only trustworthy if detection is reliable. Which makes it a verification requirement wearing an interface costume. The interface being v0 does not mean verification is deferred; it means verification is the first thing the interface is honest about, which is exactly what shadow mode measures.

The Orchestration System

Claude Code agent-orchestration system: one orchestrator the user talks to, single-responsibility subagents (jira / analyst / planner / executor / tester / verifier / committer) reporting only upward, worktree-per-feature, Docker sandbox, ephemeral resources, local web observability app, terminal-first, token-minimal.

Goal — build the factory floor Deep uses to build other products; it must generalise across projects, not one repo.

Assumption Reversal

33 ideas · S1·001–033

Opening insightThe spec rests on 14 unexamined assumptions; flipping each is the fastest route to the design space Deep has not seen.

  1. S1·001Interrupt budget: each subagent gets N human-interrupt tokens per feature, spending one reaches Deep directly — makes attention a priced resource instead of orchestrator whim
  2. S1·002Escalation auction: blocked agents bid their interrupt budget, highest-value question surfaces first, Deep answers one question not a queue
  3. S1·003Name the orchestrator role precisely as The Interviewer — its real job is question compression, merging 5 subagent questions into 1 human question
  4. S1·004Blackboard architecture: no agent-to-agent messaging, but a shared append-only blackboard per worktree, any agent reads, only section owner writes
  5. S1·005Read-only peering: agents may read each other outputs but may never ask each other anything — kills round-trips while preserving report-upward rule
  6. S1·006Transcript tax: every orchestrator-relayed message logs its token cost to the dashboard so coordination overhead becomes a visible first-class metric
  7. S1·007Enforce domain ownership with capability tokens not policy — the jira credential exists in exactly one sandbox, so agents cannot disobey what they cannot reach
  8. S1·008Tool-server subagents: jira/github/slack are not agents but MCP servers with a tiny LLM in front for intent translation — cheaper, deterministic, cacheable
  9. S1·009Deterministic shim first: jira agent answers 80 percent of calls from a typed API with zero LLM tokens, escalating to a model only for fuzzy lookups
  10. S1·010Worktree hibernation instead of destruction: snapshot container plus db to a tarball, delete compute, resurrect instantly when the feature reopens
  11. S1·011Destroy on merge plus 24h post-mortem window so a bad merge can be inspected with its original environment still alive
  12. S1·012Keep the artifact kill the compute: worktree dies but the flight recorder (transcripts, diffs, decisions, costs) persists forever and is indexed for future retrieval
  13. S1·013Codebase-region agents: agents own directories not verbs, so an auth agent accumulates real expertise in its region across many features
  14. S1·014Verbs × regions matrix: role agents stay stateless, region agents are stateful memory-holders that role agents consult before acting
  15. S1·015The Historian subagent: only job is answering have-we-done-this-before from the flight-recorder index — cheap model, big retrieval index
  16. S1·016Minimal output is a false economy when it causes rework — measure tokens-per-merged-feature not tokens-per-call
  17. S1·017Structured output not short output: enforce a JSON schema per agent to get compression and machine-checkable handoffs simultaneously
  18. S1·018Two-channel output: thin control channel (schema, enters orchestrator context) plus fat evidence channel (disk/dashboard, never enters context unless requested) — verbosity becomes free
  19. S1·019Reframe the scarce resource as orchestrator context window not tokens — design for what the orchestrator must hold, let everything else be fat and on disk
  20. S1·020Speculative parallel execution: planner emits 3 plans, 3 executors run in 3 worktrees at once, verifier picks the winner — compute is cheap, Deep time is not
  21. S1·021Test-first inversion: tester runs FIRST and writes failing tests from the feature description, making executor definition-of-done mechanical and killing verify ambiguity
  22. S1·022Backward chaining from the commit: start by writing the commit message and PR description, work backwards to the diff required — forces intent clarity up front
  23. S1·023Steerable dashboard: click any running agent to pause, inject a note, kill, or fork it — observability without control is just anxiety
  24. S1·024Time-travel replay: scrub the timeline backward, change one decision, re-run from that point — the flight recorder makes this possible
  25. S1·025Build the TUI first and the web app as a second renderer of the same event stream — Deep is a terminal multitasker, one event log two front-ends
  26. S1·026Cost heat-map: color the timeline by dollars rather than duration to expose which agent is the money pit at a glance
  27. S1·027Answer-from-repo first: every clarifying question must be attempted against code, git history and past features before reaching Deep — track the deflection rate as a metric
  28. S1·028Decision ledger: every answer Deep gives becomes a durable reusable project rule, checked before any agent asks again — answer once never again
  29. S1·029Ambient backlog: orchestrator watches jira, CI failures and flaky tests and proposes features to Deep rather than waiting to be prompted
  30. S1·030Extend the pipeline past merge with deploy agent, canary watcher and auto-revert — done becomes a production metric not a git event
  31. S1·031Resource pool with leases: pre-warmed postgres/redis containers leased to worktrees and wiped on return, killing per-feature cold-start cost
  32. S1·032Model ladder with automatic promotion: every subtask starts on the cheapest model and retries on a stronger one only on failed verification
  33. S1·033Escalation telemetry is a map of where cheap models fail, and it auto-tunes the default model assignment over time

Morphological Analysis

26 ideas · S1·034–059

Opening insightThe design space has 15 independent parameters (topology, specialization axis, isolation unit, resource lifecycle, human touchpoint, memory scope, model assignment, comms medium, trigger, verification, failure handling, observability transport, concurrency, state persistence, cost control) — Deep’s spec picks one value each, leaving most combinations untried.

  1. S1·034Git-as-the-message-bus: agents communicate by committing to the worktree, every handoff is a commit, the timeline IS git log — audit, replay and observability come free
  2. S1·035Git notes for agent metadata: attach reasoning, cost and decisions to commits via git notes so context travels with the repo and needs zero extra infra
  3. S1·036OTel-native instrumentation: every agent turn is a span, the dashboard is just a trace viewer — reuse Jaeger/Grafana instead of building observability from scratch
  4. S1·037SQLite append-only event store per feature: single portable file the dashboard tails, crash-safe, trivially inspectable
  5. S1·038Event-sourced system state: state is a fold over the event log, agents are crash-safe, the dashboard is just a projection
  6. S1·039Hierarchy of orchestrators: a feature-orchestrator per worktree plus a meta-orchestrator across features as the thing Deep talks to — scales to N parallel features without context explosion
  7. S1·040Risk-tiered agents classified by blast radius (read-only, writes-code, writes-prod, spends-money) with different approval gates and sandbox strictness per tier
  8. S1·041Approval gates replace questions entirely: agents make assumptions, record them in an assumption log, Deep approves or rejects at gate points instead of answering a question queue
  9. S1·042Async question inbox: questions accumulate and Deep batch-answers them like email — never interrupted, fits terminal multitasking
  10. S1·043Task-complexity router: a tiny classifier scores file count, diff size and ambiguity, then routes to haiku/sonnet/opus per task instead of fixed per-agent models
  11. S1·044Cross-repo global memory: patterns learned building product A are available when building product B — this is the actual leverage of one-system-many-products
  12. S1·045Per-region memory files: every directory gets an auto-maintained AGENTS.md that agents update as they learn, so memory lives beside the code it describes
  13. S1·046Two-tier verification economics: typecheck, lint and tests as gate 1 (free, deterministic), LLM review as gate 2 — never pay for gate 2 if gate 1 fails
  14. S1·047Canary-as-final-verifier: for products with production traffic, the last verification step is real users not another model
  15. S1·048Three-tier isolation ladder chosen by risk classification: in-place edit for a typo, branch-only for small changes, full worktree plus container for real features
  16. S1·049Generalist model with tool-scoped personas: no separate agents at all, just one model with different system prompts and different tool grants — an agent is merely a capability profile
  17. S1·050Agent as a pure function: stateless, takes a typed input file, emits a typed output file — fully resumable, unit-testable, and replayable
  18. S1·051Deterministic workflow engine with LLM only at the leaves: the pipeline is code, not a model deciding what comes next — huge token savings and far higher reliability
  19. S1·052Dry-run mode: the whole pipeline executes against a mock executor to show the plan and a cost estimate before a single real dollar is spent
  20. S1·053Shadow mode benchmarking: run the system against a feature Deep already built and diff its output against the real commit — earn trust empirically before delegating
  21. S1·054Cost-per-feature leaderboard: historical table of feature vs cost vs rework rate used to tune the system with evidence instead of intuition
  22. S1·055Dollar cap with graceful degradation: at 80 percent of budget the system downshifts every agent to the cheapest model and narrows scope rather than dying
  23. S1·056Wall-clock cap per feature forcing agents to report partial progress, preventing silent runaway
  24. S1·057Step cap per agent as the cheapest possible infinite-loop guard
  25. S1·058Pooled warm containers plus snapshot-hibernate: worktree state snapshots into the pool on pause, eliminating cold-start on both provision and resume
  26. S1·059N-plans-parallel then vote: three planners produce three plans, the orchestrator merges or picks, cost is trivial compared to executing the wrong plan

TRIZ Contradiction

24 ideas · S1·060–083

Opening insightTwelve core contradictions sit inside the spec — each one Deep currently resolves by trading off, and TRIZ says most can be won on both sides by separating in time, space, or scale.

  1. S1·060Context contradiction (agents need rich context but must emit few tokens) resolved by separation in space: rich context lives in the agent’s own scratch on disk, only a thin schema crosses the boundary
  2. S1·061Same contradiction resolved by separation in time: rich context during the exploration turns, compressed summary only at handoff — compression becomes a pipeline step not a standing constraint
  3. S1·062Retrieval-not-injection: agents pull the context they need on demand rather than being handed everything up front, making context cost proportional to actual need
  4. S1·063Orchestrator holds pointers not content: a manifest of artifacts with one-line summaries, reading a full artifact only when a decision requires it — orchestrator context is an index not a library
  5. S1·064Rolling orchestrator: re-instantiate the orchestrator per phase from a durable state file so context never accumulates — state is on disk, context is disposable
  6. S1·065Autonomy-versus-control dissolves once the real variable is named as reversibility not trust — auto-approve reversible actions, gate irreversible ones
  7. S1·066Undo-first design: engineer everything to be reversible (worktree, branch, canary, auto-revert) and then full autonomy becomes safe by construction
  8. S1·067Merge-conflict predictor: a cheap agent checks which files in-flight features touch and serializes only the overlapping ones — isolation by default, coordination only on collision
  9. S1·068Shared read-only knowledge base plus per-feature code overlay: knowledge is shared while code stays isolated, winning both sides of the isolation contradiction
  10. S1·069Split the jira agent into a deterministic cache plus an LLM shim so the ownership bottleneck disappears — 80 percent of requests become local reads
  11. S1·070Read-replica pattern for owned domains: any agent may read a cached snapshot, only the owning agent may write — preserves single-writer discipline without serializing readers
  12. S1·071Provision-ahead: predict resource needs from the plan and warm containers during the planning phase, hiding provisioning latency in time that was already being spent
  13. S1·072A cheap executor paired with a stronger reviewer is frequently cheaper than a strong executor alone — buy verification not generation
  14. S1·073Decomposition as a cost strategy: when a cheap model fails, the right move is often splitting the task smaller rather than escalating to a bigger model
  15. S1·074Fidelity sampling for observability: full transcripts retained for failed runs, compressed summaries for successful ones — detail where it actually pays
  16. S1·075Observability written by the runtime not by the agents: the harness records what agents did so agents never spend tokens describing themselves — free telemetry
  17. S1·076Parallelism bounded by conflict domain rather than by a fixed count: run as many features at once as have disjoint file sets
  18. S1·077Two-phase sandbox: a provisioning phase with network access to install dependencies, then network-off for execution — safety and capability separated in time
  19. S1·078Egress allowlist proxy so agents keep network access but only to approved hosts, every call logged
  20. S1·079Pipeline the phases so verification of feature N runs concurrently with planning of feature N+1, hiding verification latency entirely
  21. S1·080Progressive verification: lint on every file write, tests on every logical chunk, full suite once at the end — fast feedback without paying full-suite cost repeatedly
  22. S1·081Generic engine plus per-project profile: the orchestration engine is universal and every scrap of project knowledge lives in one profile file (stack, commands, conventions, resources)
  23. S1·082Bootstrap agent whose only job is analyzing a brand-new repo and authoring its project profile — the system onboards itself to each new product
  24. S1·083Surface the currently binding constraint in the dashboard (is it cost, context, wall-clock, or conflicts) so Deep always knows which bottleneck to attack next

Predator and Prey

24 ideas · S1·084–107

Opening insightFifteen predators stalk this system — context poisoning, cost blowout, plausible-but-wrong code, merge hell, orchestrator bottleneck, trust collapse, nondeterminism, secret leakage, destructive actions, spec drift, model deprecation, maintenance burden, alert fatigue, tool outages, sandbox escape.

  1. S1·084Immune checkpoint against context poisoning: a cheap sanity agent validates every artifact against the ORIGINAL feature request before it propagates downstream
  2. S1·085Re-grounding rule: every agent re-reads the original request verbatim, never a summary of a summary — prevents generation loss through the pipeline
  3. S1·086Provenance tags on every claim so a wrong output can be traced back to the exact agent and step that introduced the error
  4. S1·087Metabolic cap with hibernation reflex: a hard dollar ceiling per feature where the system sleeps and pings Deep rather than burning through the night
  5. S1·088Cost anomaly detector that alerts when spend-per-step deviates from the historical baseline for similar features
  6. S1·089Adversarial tester agent as a deliberate predator: its job is to BREAK the implementation, not confirm it, and it is rewarded for finding failures
  7. S1·090Property-based tests over example tests so plausible-but-wrong code has nowhere to hide
  8. S1·091Territorial marking: features declare their file territory up front and the orchestrator refuses overlapping concurrent features or forces rebase-early
  9. S1·092Trust earned in phases: phase 1 the system only analyzes and proposes while Deep merges manually, and autonomy is unlocked per risk tier as measured accuracy accrues
  10. S1·093Determinism pinning: temperature zero where possible, pinned model versions, full inputs recorded so any run is replayable, with nondeterminism quarantined to explicitly creative steps
  11. S1·094Secrets never enter context: credentials injected as env vars into the tool-server container only, with output scanners redacting patterns before anything is logged or posted
  12. S1·095No claws in the sandbox: the executor container holds no push rights and no prod credentials, and only a separate gated committer agent can push, never force-push
  13. S1·096Protected branches as the immune barrier — the last line of defense that holds even when every agent-level guard fails
  14. S1·097Spec echo: before any code is written the orchestrator restates the feature as acceptance criteria for Deep to confirm in one keystroke — the cheapest possible drift-killer
  15. S1·098Prompt and model abstraction layer plus a golden-task regression suite, so swapping models becomes a tested migration rather than a leap of faith
  16. S1·099Biggest real predator is maintenance burden — the orchestrator eating the very time it was built to save — so build on Claude Code existing primitives (subagents, hooks, MCP, worktrees) as config plus small scripts, never a bespoke platform
  17. S1·100Dashboard shows exceptions by default with the full timeline available on demand — silence should mean success, or alert fatigue kills the tool
  18. S1·101Circuit breaker plus cached read-replica so a jira outage degrades to a stale read instead of halting the entire pipeline
  19. S1·102Least-privilege container: read-only root filesystem, only the worktree mounted, no docker socket, non-root user, dropped capabilities, seccomp profile
  20. S1·103Design for the real predator — Deep’s own future self at 2am — by favoring boring inspectable state (files, git, sqlite) over clever distributed machinery
  21. S1·104Escape hatch command that dumps all in-flight work to an ordinary branch and detaches the system, so manual takeover is always one keystroke away
  22. S1·105Playing dead: on repeated failure the system halts, writes a complete handoff document, and gets out of the way rather than thrashing expensively
  23. S1·106Rate-limit aware scheduling for external tools, with the owning agent holding a token bucket the rest of the system cannot deplete
  24. S1·107Chaos drill as an architecture test: kill a random agent mid-run and see whether the system degrades or halts

Swarm Logic

20 ideas · S1·108–127

Opening insightForbidding the master plan exposes that most of the orchestrator’s job is work ASSIGNMENT, which a shared queue plus local rules does for free — the orchestrator’s real irreducible job is the human contract, not coordination.

  1. S1·108Stigmergy via the filesystem: agents leave marks (failing tests, TODO files, lint errors) and other agents are attracted to them — a failing test IS the pheromone, no coordinator required
  2. S1·109Three dumb local rules replace the assignment logic: fix a failing test you can fix, claim any work item matching your capability, write a note and die if you cannot progress in N steps
  3. S1·110Claim-by-lockfile work distribution eliminates the assignment step entirely and makes concurrency safe with no central scheduler
  4. S1·111Ant-colony task allocation with response thresholds: the longer a task waits and the more important it is, the more likely a lower-threshold agent picks it up — load balances itself
  5. S1·112Emergent decomposition: rather than a planner breaking the feature down, spawn agents that each attempt the whole feature and abort where competence runs out, leaving a note — the breakdown is discovered not designed
  6. S1·113Evolutionary variant selection: N executors, brutal selection on test pass rate and diff size, then breed the survivor approach into the next round
  7. S1·114Quorum sensing as a spec-drift defense: do not begin executing until 2 of 3 analysts independently converge on the same interpretation of the request
  8. S1·115Waggle dance: an agent that found a productive approach broadcasts a compact how-I-did-it that other agents copy, giving cross-feature learning without designing a central memory
  9. S1·116Termite-mound bounded build: agents may only modify files adjacent to already-changed files, naturally constraining diff sprawl
  10. S1·117Capability-tagged work queue where agents pull what matches their profile — adding a new agent type is just adding a new puller, making the system trivially extensible
  11. S1·118Death as a feature: agents are cheap and mortal, any agent exceeding its step budget dies and leaves its partial work as a pheromone for the next one — robustness through disposability
  12. S1·119In a swarm there is no jira agent, jira is simply another pheromone source polled into the shared work queue
  13. S1·120Local rules generate observability for free — the event log of claims, releases and deaths IS the timeline the dashboard renders
  14. S1·121Pheromone decay: stale work items lose priority and eventually expire, preventing a growing graveyard of half-finished tasks
  15. S1·122Recruitment instead of escalation: a stuck agent raises its pheromone to attract a stronger model rather than escalating up a chain of command — the model ladder as swarm recruitment
  16. S1·123No global state at all: everything an agent needs lives in the worktree it is standing in, giving portability and resumability for free
  17. S1·124Minimal viable swarm is radically cheaper to build than eight bespoke role agents — three rules, one shared queue, N identical workers differing only in tool grants
  18. S1·125Anti-fragility architecture test: kill a random agent mid-run, because a swarm shrugs where a pipeline halts
  19. S1·126The honest synthesis is hybrid — swarm dynamics for the messy divergent middle (analysis, planning, exploration), strict pipeline for the convergent human-facing edges (spec confirmation, commit, merge)
  20. S1·127Swarm for exploration and pipeline for delivery makes the orchestrator responsible only for the two boundaries Deep actually cares about: what was asked, and what shipped
Session 1 · Synthesis
  1. Two-channel output, orchestrator-holds-pointers and runtime-writes-telemetry are one principle — separate the control plane from the evidence plane; build the evidence plane once and all three come free.
  2. Git-as-message-bus solves comms, observability, replay, flight recorder and swarm stigmergy with a single decision.
  3. Capability tokens convert the jira ownership rule from policy into physics — agents cannot disobey what they cannot reach.
  4. Reversibility not trust is the hidden axis under the autonomy dial, trust collapse and risk tiers — blast radius is engineerable.
  5. Deep optimized the wrong resource: compute is pooled and cheap, context and history are scarce, so recycle compute aggressively and keep artifacts forever.
  6. Minimal-output-to-save-tokens was the wrong goal — three lenses converged independently; the metric is tokens-per-merged-feature and terseness barely moves it while causing rework.
  7. The Historian plus cross-repo memory plus waggle dance are one idea — memory across features and products is the compounding advantage and is absent from the current spec.
  8. BreakthroughMake the orchestrator a dumb deterministic workflow engine with intelligence only at the leaves; the orchestrator is a conversation and a scheduler fused together that should be split, leaving only the Interviewer as a live LLM.
  9. Build order: event log plus git-as-bus, then deterministic engine with 3 agents not 8, then TUI on the event stream, then shadow mode to measure, then earn autonomy — shadow mode and dry run exist to tell Deep when to STOP building, the defense against maintenance burden as the likeliest project-killer.

Job to Be Done

19 ideas · S2·001–019

Opening insightThere is no single thing called memory — there are about ten distinct jobs with different shapes, lifetimes and retrieval patterns, and building one vector store for all of them is the classic failure.

  1. S2·001Job 1 do not make me explain my conventions twice — but the best form of a remembered convention is not retrieval, it is a generated lint rule or test that fails the build, costing zero tokens at read time
  2. S2·002Memory that enforces itself beats memory that must be recalled — convert every remembered preference into an executable check wherever the preference is checkable
  3. S2·003Job 2 do not rewrite code that already exists — prior-art retrieval keyed on the PLAN not the prompt, running after decomposition using concrete subtasks as queries
  4. S2·004Job 3 do not repeat a mistake that already cost money — and the right artifact for a remembered failure is a regression test, not a note
  5. S2·005Job 4 make an agent productive in an unfamiliar region of the repo fast — region expertise memory attached to directories
  6. S2·006Job 5 let product B benefit from product A — cross-repo pattern memory, the only job that justifies the whole system existing across projects
  7. S2·007Job 6 tell me WHY the code is like this — rationale memory whose primary consumer is human, so it must be readable prose not machine soup
  8. S2·008Job 7 estimate what this feature will cost before committing budget — historical cost memory answering features touching auth have averaged X dollars and Y rework cycles
  9. S2·009Job 8 know which areas are fragile and which tests are flaky — risk memory used as a ROUTING input that selects verification depth, not as context
  10. S2·010Job 9 resume a feature paused three weeks ago — episodic memory, which is just an append-only per-feature log and is nearly free
  11. S2·011Job 10 survive a model version change without re-teaching everything — memory stored as structured facts rather than tuned prompt text
  12. S2·012JTBD reframe: Deep is not hiring memory, he is hiring do-not-waste-my-attention-twice — every memory feature must be justified by a specific attention saving
  13. S2·013Memory write is a privilege not a default: only verified and merged outcomes may write to long-term memory, failed experiments write to episodic only — this is the primary defense against memory poisoning
  14. S2·014Every memory entry carries a decay policy chosen at write time — permanent, until-refactor, N-features, or this-session-only
  15. S2·015Learning is a pipeline step with an owner: the committer agent writes what was learned, so memory is a first-class output rather than a hopeful side effect
  16. S2·016Hard read budget per feature caps how many tokens of memory may enter context, which forces ranking quality to actually matter instead of being decorative
  17. S2·017Negative memory — we tried this and it did not work — is higher value per token than positive memory and almost nobody builds it
  18. S2·018The decision ledger should record the QUESTION SHAPE alongside the answer so similar-but-not-identical questions can be recognized and deflected
  19. S2·019If a new human developer cannot read the memory store, it is too machine-shaped to audit and will silently rot

Nature’s Solutions

19 ideas · S2·020–038

Opening insightBiology solved memory many times over and the transfers are unusually literal here — the strongest is sleep consolidation, which says do not write long-term memory during the run at all.

  1. S2·020Sleep consolidation (hippocampus to neocortex): a consolidation job runs BETWEEN features or nightly, compacting fast lossy episodic logs into slow structured durable facts — tokens are cheap then and outcomes are finally known
  2. S2·021Immune memory and memory B cells: remember specific threats and respond faster on re-exposure, so a past bug pattern triggers a pre-emptive check when something similar appears
  3. S2·022Vaccination: deliberately re-expose the system to a past bug so it builds an antibody in the form of a permanent test
  4. S2·023Bacterial CRISPR literally stores fragments of past viral attackers in its own genome — store the diff that caused each past incident as a recognition signature
  5. S2·024Synaptic pruning: memory entries that are never retrieved get deleted, so track retrieval hit-counts from day one or you can never prune safely
  6. S2·025Myelination: frequently retrieved memories get promoted into the always-loaded project profile while rare ones stay in cold retrieval
  7. S2·026DNA versus epigenetics: cross-repo memory is the slow shared genome, the per-repo profile is the fast local epigenetic layer that switches genes on and off
  8. S2·027Spores and seeds: a tiny seed file per repo that can regenerate the entire memory index from git history, so losing the index is an inconvenience not a catastrophe
  9. S2·028Coral and stromatolites: structure accreted by many small organisms each building on the last skeleton — the codebase and its AGENTS.md files ARE the memory, accreted feature by feature
  10. S2·029Octopus distributed cognition puts most neurons in the arms — per-directory memory located where the work happens beats a central store
  11. S2·030Elephant matriarch holds long-term ecological memory the herd relies on only in crises — the Historian should be consulted at decision points, not constantly
  12. S2·031Migratory magnetoreception navigates by a stable external field — anchor memory to the most stable references available, never to line numbers
  13. S2·032Slime mold rebuilds optimal networks by reinforcing used paths and starving unused ones — the retrieval graph itself becomes the memory, with structure encoding what matters
  14. S2·033Tardigrade cryptobiosis: suspend completely and resume losing nothing — the model for hibernating a paused feature
  15. S2·034Squirrel scatter-hoarding accepts that some caches are lost — embrace lossy redundant memory over a perfect fragile index
  16. S2·035Bird song learning has a critical period with a tutor then crystallizes — learn intensively during repo bootstrap, then stabilize the profile
  17. S2·036Forgetting is adaptive: organisms forget specifics to generalize, and aggressive forgetting of specifics while keeping the pattern is what stops memory becoming a liability after refactors
  18. S2·037Lichen symbiosis: two organisms whose combined memory exceeds either — the codebase holds structure, the event log holds history, and neither alone is memory
  19. S2·038Horizontal gene transfer lets bacteria swap useful genes across species lines — a deliberate mechanism to transplant a proven pattern from repo A into repo B, not merely hope retrieval finds it

Cross-Pollination

23 ideas · S2·039–061

Opening insightMemory is a solved problem in a dozen industries, and the single biggest scope cut available is realizing git already IS most of the memory store Deep was planning to build.

  1. S2·039Databases: write-ahead log plus compaction is exactly the episodic-log plus consolidation pattern, arrived at independently from sleep biology — two fields converging is a strong signal it is correct
  2. S2·040Databases: separate the index from the store so the index can be rebuilt, reshaped or thrown away without touching the durable record
  3. S2·041Databases: materialized views as precomputed answers to the questions agents ask most, refreshed on merge rather than computed per query
  4. S2·042Version control: git blame and git log already ARE memory, so build nothing that stores what git can already answer — the largest single scope reduction available
  5. S2·043Search engines: memory from merged and shipped code must rank above memory from an abandoned branch — authority and recency signals, not raw similarity
  6. S2·044CPU cache hierarchy: design memory explicitly as tiers with sizes and latencies — always-loaded profile as L1, per-region AGENTS.md as L2, retrieval index as L3, raw git history as disk — with defined promotion and eviction between them
  7. S2·045Zettelkasten: atomic notes, one fact each, densely linked, structure emerging from links rather than an imposed taxonomy
  8. S2·046Aviation and NTSB: a flight recorder plus mandatory incident reports, where a single finding becomes an airworthiness directive binding on every aircraft — an incident in one repo becomes a guardrail in all of them
  9. S2·047Medicine: a repo has a chart — known allergies (what breaks it), chronic conditions (tech debt), past procedures (major refactors) — and you read the chart before operating
  10. S2·048Law and precedent: decisions cite prior decisions, and a decision can be explicitly OVERRULED with a stated reason while the old one stays visible — this is the clean answer to memory that has become wrong
  11. S2·049Accounting double-entry: every memory claim carries provenance and can be audited back to its source event
  12. S2·050Library science: a controlled vocabulary for tags so the store stays queryable as it grows past the point where anyone remembers what they called things
  13. S2·051Wikipedia: contested facts get flagged rather than silently overwritten, and memory needs a review mechanism once more than one agent writes to it
  14. S2·052Kitchen mise en place: pre-warm the memory context for a feature during the planning phase so execution never stalls waiting on retrieval
  15. S2·053Casino player tracking: compute expected value per area of the codebase and learn which regions reliably cost more than estimated
  16. S2·054Sports film study reviews losses more than wins — consolidation should weight failures substantially higher than successes
  17. S2·055Toyota production system: standard work is convention memory, the andon cord is the escalation path, and every kaizen is a memory write with a named owner
  18. S2·056Actuarial tables price risk from history — route model tier and verification depth by the historical risk profile of the area being touched
  19. S2·057Tradecraft compartmentalization: memory scoped by agent capability, so the executor never receives the entire project history it does not need
  20. S2·058Jazz standards: a shared repertoire everyone knows is what makes improvisation fast — a library of known-good patterns per stack is the highest-leverage memory content
  21. S2·059Chess opening books: precomputed known-good sequences for common positions, so common feature shapes (add a CRUD endpoint, add a migration, add a webhook) get a stored opening
  22. S2·060Air traffic control flight strips: the compact record handed between controllers means the agent-to-agent handoff artifact is itself the memory unit
  23. S2·061Changelogs and semver: memory of what changed and why, in a format humans already know how to read

Time Horizon Ladder

18 ideas · S2·062–079

Opening insightStepping the memory layer through 1, 100, 1 000 and 10 000 features shows the dominant cost FLIPS from writing memory to invalidating it, which reverses what the design should optimize for.

  1. S2·062At one feature memory is pure overhead — v0 should contain NO memory layer at all, only the episodic event log, which is free and quietly becomes the substrate everything else is built from later
  2. S2·063At roughly twenty features the decision ledger starts paying, and conventions memory should be built first because it has the highest hit rate, the smallest size and the cheapest retrieval
  3. S2·064At roughly one hundred features naive load-all-memory breaks and real indexing plus ranking becomes mandatory, as does the consolidation job
  4. S2·065At roughly one thousand features memory ROT dominates — most entries reference code that no longer exists — and decay, pruning and re-validation become the main engineering problem
  5. S2·066At ten thousand features memory is a product with its own maintenance burden, so it must be mostly DERIVED and recomputable from git rather than stored, or the maintenance predator returns and wins
  6. S2·067Across five repos patterns transfer, but across fifty the per-repo noise swamps cross-repo signal unless cross-repo memory stores only abstract patterns and never concrete snippets
  7. S2·068What transfers between products is how-we-do-auth, never the auth code itself — this single rule determines the schema of cross-repo memory
  8. S2·069What survives every rung of the ladder is the append-only event log and git itself, because both are immutable and always true
  9. S2·070What breaks at every single rung is anything storing file paths, line numbers or code snippets
  10. S2·071Design rule falling out of the ladder: memory stores questions and their durable answers plus pointers to stable anchors, never copies of code
  11. S2·072Stable anchors ranked by durability: test names beat public API symbols beat module names beat file paths, and line numbers are never acceptable anchors
  12. S2·073Hook memory invalidation to the refactor itself — the committer detects renames and rewrites anchors as part of the commit, so memory cannot drift behind the code
  13. S2·074Periodic re-validation sweep samples memory entries and checks their anchors still resolve, flagging the dead ones instead of waiting to be misled by them
  14. S2·075Make memory rebuildable: if ninety percent can be regenerated from git history plus the event log, then corruption stops being a crisis and the schema becomes free to change
  15. S2·076At the ten-year rung the model has changed many times — memory as structured facts and tests survives that, memory as tuned prompt text does not
  16. S2·077At the absurd far rung the memory becomes more valuable than the code, because code is regenerable while accumulated decisions and constraints are not — which inverts what you back up and what you version
  17. S2·078The consolidation job is the ONLY genuinely new subsystem worth building for memory, because everything else is querying git and the event log
  18. S2·079Measure memory ROI directly as retrieval token cost versus measured reduction in rework, and delete the memory layer outright if that number is not positive
Session 2 · Synthesis
  1. ConvergenceStrongest signal is convergence — sleep consolidation in biology and write-ahead-log plus compaction in databases are the same design reached independently, both saying never write long-term memory during the run; log fast and lossy, consolidate afterward when outcomes are known and tokens are cheap.
  2. Biggest scope cut: git already IS most of the memory store, so build nothing git log and git blame can answer, and require memory to be rebuildable from git plus the event log — memory becomes an index over things already held, making schema change free and corruption survivable.
  3. Key reframe: memory that enforces itself costs zero tokens at read time — conventions become lint rules, failures become regression tests, incidents become guardrails, so the layer’s real job is CONVERTING memory into executable artifacts and falling back to retrieval only for the irreducibly fuzzy.
  4. The trap from the horizon ladder is that dominant cost flips from writing memory at 100 features to INVALIDATING it at 1000, so decay policy at write time, durability-ranked anchors with line numbers banned, and invalidation hooked to the refactor commit must all be day-one decisions.
  5. Two cheap unbuilt wins: memory as a ROUTING input (risk memory picks verification depth, cost memory picks model tier) and negative memory, which is worth more per token than positive memory.
  6. Cross-repo memory must store abstract patterns never snippets — how-we-do-auth, not auth code — and that single rule determines the schema.
  7. v0 verdict agrees with session one: build no memory layer, keep only the episodic event log, which is simultaneously flight recorder, timeline, resume mechanism and the substrate for everything later.
  8. Self-referential: the memlog pattern this session ran on — append-only, one line per idea, never edited, single consolidation pass at the end — IS the architecture to build.

The Human Interface

The human interface to the agent orchestration system — what talking to the Interviewer actually feels like at 9am with three features in flight: question compression, spec echo, interruption design, ambient awareness, terminal-first ergonomics, trust and handoff.

Goal — design the one component that must stay a live LLM conversation; if this feels bad Deep abandons the system regardless of how good the machinery is.

Empathy Map

16 ideas · S3·001–016

Opening insightDeep at 9am with three features in flight says what is the status and did it ask me something, thinks is it stuck or thinking, and I could have done this myself by now, does constant alt-tabbing and diff-skimming between meetings, and feels low-grade spend anxiety plus guilt about not reviewing properly.

  1. S3·001Status must be answerable in under two seconds WITHOUT reading — one glanceable line per feature, and if a paragraph is needed to know the state the interface has already failed
  2. S3·002Visually distinguish stuck from thinking, because that ambiguity is the single largest source of anxiety — a heartbeat pulse naming the current step, never an undifferentiated spinner
  3. S3·003Deep’s three-feature mental model decays fast between meetings, so every notification must reload the context itself rather than assuming he still holds it
  4. S3·004Never interrupt with anything that cannot be resolved in ten seconds — anything longer gets queued for a boundary
  5. S3·005Batch interruptions to natural boundaries with a do-not-disturb-until mode that queues questions rather than firing them into a meeting
  6. S3·006Cost needs a permanently visible running number, because spend anxiety is continuous and a report he has to request does not relieve it
  7. S3·007He skims diffs rather than reading them, so the system must say WHERE to look — the risky twelve lines of a four-hundred-line diff — giving review guidance instead of review dumps
  8. S3·008I-could-have-done-this-myself is the churn signal, so surface elapsed-versus-estimate continuously to enable killing early instead of sunk-costing
  9. S3·009The system must state its own confidence AND what it did not verify, so trust is calibrated rather than blind and the guilt about skipping review is resolved honestly
  10. S3·010Make just-do-it a real first-class command meaning stop asking, use judgment, I will review at the end
  11. S3·011Make rejection cheap: one keystroke plus a reason, and that reason becomes a decision-ledger entry automatically
  12. S3·012Answer in the terminal he is already in — the web app is for LOOKING, the terminal is for ANSWERING, and never force a context switch to reply
  13. S3·013Every question carries its own mini-brief so it is answerable without loading the full feature context back into his head
  14. S3·014Target the emotional register of a competent colleague reporting in, not a dashboard demanding attention
  15. S3·015Silence must be a trustworthy contract meaning no news is good news, or he will poll anxiously and the whole ambient design collapses
  16. S3·016Show what he actually asked for alongside what is being built, because at 9am he does not remember his own 4pm phrasing

  6. S3·022Worst: requires the web UI to do anything. Flip: terminal-complete with the web app strictly optional

Sci-Fi Artifact From the Future

15 ideas · S3·038–052

Opening insightDescribing concrete artifacts from the world where this already works — actual terminal messages, cards and commands — forces specificity that abstract interface principles never reach.

  1. S3·038The morning brief: six lines at 9am — three features, one needs you for thirty seconds, one merged overnight for two dollars ten, one blocked on a flaky payments test seen four times before — which reverse-engineers into overnight autonomy, cost tracking, pattern memory and triage ranked by attention cost
  2. S3·039The one-question interrupt card shows the question, the recommended answer, the consequence of each option, AND what it will do if he says nothing in ten minutes — default-on-timeout is the mechanic that makes async tolerable

  4. S3·041The kill card: feature X has spent eight dollars and forty minutes against a three dollar fifteen minute estimate — continue, narrow scope, kill, or take over — making early exit a designed moment rather than a failure
  5. S3·042The handoff document written when the system gives up reads like a colleague note, not a stack trace, and is the artifact that determines whether giving up feels like competence or failure
  6. S3·043The review request: twelve of four hundred lines need your eyes, and here is why each one does
  7. S3·044The weekly self-report: fourteen features shipped, you corrected me three times, here is what I learned, and here are two rules I would like to add to the ledger — the system proposing its own memory writes for approval
  8. S3·045The trust meter: per-area accuracy history like auth nine of ten merged unchanged, payments three of seven — autonomy derived from evidence rather than granted by vibes

  15. S3·052The receipt: a single end-of-day summary of spend and outcomes that resolves the anxiety daily instead of letting it accumulate

Shadow Work Mining

14 ideas · S3·073–086

Opening insightWhat Deep is actually avoiding is more predictive of adoption than any feature — the fears are owning incomprehensible code, losing the feel of his own codebase, burning money while asleep, and quietly preferring to build the tool rather than the products.

  1. S3·073Fear of owning code he does not understand means comprehensibility is a hard requirement not a nicety — the system must write in HIS idiom and the review artifact must make the diff understandable, not merely correct
  2. S3·074Fear of losing the feel for his own codebase argues for deliberately keeping him in the loop on architecture while delegating mechanics — the parts he enjoys are a design input, not an inefficiency to optimize away
  3. S3·075The honest shadow is that building the orchestrator is more fun than building the products, so the real success metric must be shipping velocity of actual products, not sophistication of the tool
  4. S3·076Fear of burning money overnight is resolved not by a cap alone but by a morning receipt, so the anxiety closes daily instead of compounding
  5. S3·077Fear of looking bad when it commits something dumb makes attribution an EMOTIONAL design question — PR by default rather than direct commit, and a clear convention for whose name is on the commit
  6. S3·078Deep does not want to be the orchestrator user, he wants to be a builder with leverage, so the interface must feel like his own capability rather than a product he operates
  7. S3·079He will not do thorough reviews because reviewing is boring, so design honestly for that — make verification strong enough that skimming is the RATIONAL choice rather than building a beautiful review UI he will not open
  8. S3·080Fear of silent degradation — it works for three months then quietly gets worse — is exactly what the weekly self-report and the trust meter exist to make visible
  9. S3·081The secret wish is to describe a feature and go make coffee, which means the true north metric is percentage of features completed with ZERO mid-flight interruptions
  10. S3·082An interruption costs roughly fifteen minutes of his focus, so the system should be willing to spend a great deal of compute to avoid one — quantifying the exchange rate between tokens and attention is the single most clarifying idea for the whole interface
  11. S3·083He will blame the system for his own vague specs, and spec echo protects both parties because the echo becomes the contract
  12. S3·084Uncanny register risk: too human a question is unsettling and too robotic a question gets ignored, so aim squarely at colleague — not butler, not robot
  13. S3·085Resentment risk: if the system asks him to do something tedious that it could have done, trust drops faster than it does from an outright bug
  14. S3·086He secretly wants to be impressed, and a system that occasionally shows him something he did not know about his own codebase buys more trust than one that is merely correct
Session 3 · Synthesis
  1. Master variable is the exchange rate between tokens and attention — an interruption costs about fifteen minutes of focus, so the system should spend large amounts of compute to avoid a single question, which retroactively settles session one’s token-minimal premise because attention is orders of magnitude more expensive than tokens.
  2. Three metaphors independently produced speak-only-when-something-is-wrong, and that silence-means-success contract is only trustworthy if detection is reliable — so the silence contract is actually a verification requirement wearing an interface costume.
  3. Mode confusion is the aviation accident class already waiting in a design with autonomy tiers — permanent mode display in the prompt line, instant disengage, standard callouts at transitions; modes are how reversibility gets communicated to the human.
  4. ConvergenceThird convergence across three sessions: spec echo found via threat-modeling drift and ATC readback found via metaphor are the same mechanism reached by unrelated routes, so it is load-bearing and should be built first.
  5. Default-on-timeout is the mechanic that makes async tolerable — every question states what happens if ignored, reconciling never-block with do-not-act-unapproved and making non-response a valid input.
  6. Shadow work reframes the success metric to percentage of features completed with ZERO mid-flight interruptions, with shipping velocity of actual products as the counter-metric defending against the tool-building-as-procrastination shadow.
  7. Two unspecced essentials: attribution is an emotional design question (whose name on the commit, PR versus direct push) and the register must be colleague — not butler, not robot — warmth through competence with zero pleasantries.
  8. Build orderThe interface is not phase two, because the v0 spine exists to run shadow mode and shadow mode has no autonomy at all — it only reports — so shadow mode is entirely an interface product and the morning brief, the one-question card with default-on-timeout, and mode display ARE v0.
  9. Worst Possible Idea produced the most directly implementable output of any lens across three sessions: twenty-one irritations inverting into twenty-one concrete interface rules, effectively a free interface spec.
