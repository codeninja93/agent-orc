- (decision) ADR-004 ACCEPTED by Deep on 2026-09-22: command execution is a capability, not a built-in tool. Raised by story 2-5, the first agent that must run a command, and by ADR-001's own note that the question had to be settled before 2-5 and 2-6. ADR-003 granted Bash to implementation, testing and verification on the grounds that Bash is how a gate runs, inside the container per ADR-001 - and that sentence was measured false against CLI 2.1.278: claude -p runs on the host because the subscription credential is in the macOS keychain and cannot be mounted, the Bash tool is a built-in of that host process, and --restricted lets a permission tool approve or deny a tool use but never relocate one into a container. So a granted Bash was an uncontained host shell, and every protection AD-20 lists applied to a container the command never entered. The three declarations lose Bash; command execution becomes an MCP tool whose server runs the declared command inside the container, supplied through --mcp-config under --strict-mcp-config and pre-approved through --allowedTools because a non-interactive run has nobody to answer a permission prompt. GRANTABLE_TOOLS keeps Bash, because AD-17 lets a user-defined agent be granted anything the declared set contains - granting it yields a host shell, which is why story 2-4's elevated reporting names it. Consequences named on the record: an agent can no longer run an arbitrary command, only what the profile's mechanics.commands declares, and a repository needing another must declare it; the command-runner server becomes the one component that may start a container and is worth reviewing as such; a per-command container start costs latency, which ADR-001 already accepted; and between ADR-004 and story 2-6, which builds the server, verification has no way to run a gate at all, so the system can write a change it cannot test. What remains open is how the server authenticates that its caller is the step it claims to be - the process tree is the evidence today
- (decision) ADR-005 ACCEPTED by Deep on 2026-09-22: schema_version advances per artifact, not once for all of them. Raised by story 2-6, which added mechanics.commands.typecheck because CAP-13 names typecheck as a deterministic gate and the profile could not express it - a shape change to an artifact the installer writes, which AD-28 answers with a version bump and a refusal rather than a silent default. One shared constant made that bump global, and the consequence was measured rather than argued: with CURRENT_SCHEMA_VERSION advanced, a v1 state.json, question state and command intent are each refused, so a run in flight when the installer was upgraded could no longer be read back and AD-8's resume would have nothing to resume from - a profile field breaking every live run. So a version is now a property of one artifact: ProfileSchema reads only v2 while every other artifact still reads v1, and the profile refuses a v1 file with config.schema_version_unrecognised naming the installer. AD-28 is unweakened and the guard says so - every registered artifact still carries a version and still refuses an unrecognised one, asserted in both directions and for a missing field. Consequences named on the record: a version number alone no longer identifies an artifact, so installerVersionFor is bounded by the artifact's own policy before it names a writer - telling a person their command intent was written by installer 0.1.0 because the profile reached v2 is a confident false statement about a build that does not exist; parseVersionedArtifact reads the policy off the issue its own field raised rather than recovering it from the refusal's prose, because a refusal whose correctness depends on the wording of its own sentence is one nobody may rephrase; and the installer's re-run reads the previous version for the purpose of re-interviewing, since the re-run is the migration and an installer that refused the file whose refusal says 're-run the installer' leaves every existing install with no route forward
