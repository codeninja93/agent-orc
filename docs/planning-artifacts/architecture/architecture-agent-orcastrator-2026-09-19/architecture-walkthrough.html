Architecture Spine · SPEC-agent-orchestrator · status: final

Reconciled Pipeline

A controller-style reconciler loop owns durable on-disk state and advances each feature by at most one action per pass; each action is a pure-function pipeline stage executed as an OS subprocess; everything observable is appended to a per-run event log that is the durable truth.

01

The paradigm, in plain language

Four words carry the whole design: reconciler, durable, subprocess, append-only. Each one converts a property that would otherwise have to be maintained by discipline into one the operating system or the filesystem maintains for you. Read this before any rule below; every rule is downstream of it.

A reconciler, not a supervisor

A supervisor holds the run in memory: it knows which step is live, which container is leased, what to do next. Kill it and that knowledge is gone, so correctness depends on shutdown handlers firing in the right order — the code path least often exercised and hardest to test.

A reconciler holds nothing. Every pass it reads the checkpoint from disk, decides the single next action, takes it, writes the checkpoint back. There is no in-memory authority to lose.

What it buys: closing the laptop mid-feature is not an incident. Crash recovery, instant disengage and the escape hatch stop being features that must be written and start being consequences of the loop's shape.

Durable on-disk state, ranked

Two files per run. events.jsonl is append-only and is the truth. state.json is a checkpoint derived from it, kept only so the loop does not replay the world on every pass.

The ranking is the point. When they disagree after a crash — and they will — there is no arbitration to design: the log wins, the checkpoint is discarded and rebuilt.

What it buys: one fact never has two named authorities. Every surface — TUI, web, shadow mode, consolidation — is a projection of the same log, so no two surfaces can disagree about what happened.

Stages that are OS subprocesses

Every step agent is one claude -p process, spawned with a typed input file and a JSON schema for its output. Not a library call, not an in-process SDK object.

A subprocess is a pure function over typed files, and the process boundary is what enforces it. A stage cannot smuggle state to the next stage because there is nothing to smuggle it in. Kill and fork become trivial because the unit of work is a pid.

What it buys: statelessness is enforced by the kernel and by a recorded baseline commit, not by reviewer vigilance. Re-running a step is safe by construction rather than by promise.

An append-only event log

One JSON object per line, one file per run, one writer. Nothing is ever mutated. Adding a new event type is never a breaking change because readers are required to ignore what they do not recognise.

Every emitter — engine phases, tool servers, step subprocesses — writes the same envelope, so a single timeline renders without special cases.

What it buys: the run is debuggable with jq and tail at 2am, six weeks later, with no database to stand up. Any index is a derived projection you can throw away and rebuild.

The compound effect

Each property independently removes a class of bug. Together they remove the need for the system to be careful. A step cannot double-apply an edit (baseline reset). The engine cannot lose a run (nothing authoritative in memory). Two surfaces cannot disagree (one log). A stale answer cannot leak forward (config snapshot per run). The architecture's job is to make the failure modes structurally unavailable, so the single developer maintaining it does not have to hold them in his head.

Dependency direction

An arrow means may depend on; no edge may be reversed and no cycle may be introduced. contracts depends on nothing. No renderer, step subprocess, tool server or installer may import the engine; renderers reach it only by writing command intent files per AD-19.

04

Consistency conventions

Below the level of an AD, these are the spellings every unit shares. They are not decisions so much as the alphabet the decisions are written in.

Naming — entities, files, interfaces, events

Event type names are dot-namespaced and past-tense. The vocabulary includes step.started, agent.tool_used, fetch.recorded, write.attempted, write.executed, permission.denied, redaction.failed, budget.degraded, budget.exhausted, question.asked, question.resolved, question.default_taken, question.deflected. Feature slugs are kebab-case. Step ids are stable declared names, never positional indexes. Readers ignore unknown event types rather than erroring.

Data & formats — ids, dates, error shapes, envelopes

Run id is a ULID minted by the engine per AD-29; project-id is the first-commit SHA per AD-10. All timestamps are RFC3339 with milliseconds in UTC, carried as z.string() because z.date() is outside the structured-outputs subset. Every failure crossing a unit boundary uses the shape code, message, retryable, cause, and every code appears in the AD-35 disposition table. Human-edited configuration is TOML; machine-owned state and events are JSON; every on-disk artifact carries a schema_version per AD-28. Every schema is defined once as a Zod v4 schema and exported with z.toJSONSchema(schema, { target: "draft-7" }) — never with default arguments, since Zod 4 defaults to draft-2020-12 and the --json-schema validator rejects it. Step contracts use no recursive or self-referential schemas, no minLength, no minItems greater than one and no minimum.

State & cross-cutting — mutation, errors, logging, config, auth

One writer per file: only the reconciler writes a state.json, only the runtime recorder appends to an events.jsonl, only the committer writes the git note; one engine per ORCH_HOME per AD-30. State writes are atomic — temporary file in the same directory, then rename. Event lines are never mutated and every event passes redaction before append. No unit writes diagnostics to stdout; everything observable goes to the event log. Reconciliation is concurrent across features but serializes any features whose declared file territories overlap. Auth is the user's own Claude Code subscription login via non-bare claude -p, asserted at startup; no ANTHROPIC_API_KEY path and no bundled credential.

The pinned stack

Every row was verified against the live registry. Two of the pins are counter-intuitive enough that a future reader will be tempted to "fix" them — both were reproduced empirically and both are load-bearing. The table also now carries the two things that used to be deferred: the web surface's bundler, and the model ladder's actual rungs.

TypeScript 5.9.3 — not 7.0.2, which is newer
TypeScript 7 is real, current and shipping, but it is Project Corsa: a native Go port that ships no compiler API until 7.1. Without that API, typescript-eslint and ts-morph do not work — which means adopting 7 silently decides that the repository cannot lint itself, directly contradicting the plan to turn conventions into lint rules. TS 7 also removes ES5, AMD, UMD, SystemJS and baseUrl, and ships no musl binary, so the executor Dockerfile could not be Alpine-based. 5.9.3 is the last 5.x line and the last line shipping the compiler API. The pin is now mechanically enforced by the stack itself: typescript-eslint 8.70.0 peers typescript >=4.8.4 <6.1.0, so its peer range — not the compiler — is the blocker, and it is also the adoption trigger.
npm pinned below 12 — not "latest"
npm 12 turns off git-dependency resolution by default (--allow-git defaults to none) and disables install and prepare scripts, with the changelog stating that allow-scripts covers npx. The onboarding path in AD-12 is npx github:<owner>/<repo> init, which depends on exactly that resolution. The pin buys time: no supported Node currently bundles npm 12 (Node 24.21 bundles 11.19.0, Node 22.23.2 bundles 10.9.8), and before npm 12 becomes the bundled npm of a supported Node the delivery path must be re-verified empirically or replaced.

06

What lives where on disk

The split is one sentence: config in-repo, state central, configuration snapshotted per run. A teammate who clones the repository inherits the setup without inheriting anyone's run history, and a worktree of the repository contains only committed config that is identical in every worktree — so there is never a second copy of state with no rule for which one wins.

machine scope
ORCH_HOME/config.toml — ports, paths, docker endpoint, machine defaults. Never committed.
project scope
<target-repo>/.orch/ — profile, permissions, agent roster, manifest. Committed.
run scope
runs/<run-id>/config/ — the immutable snapshot taken at run start. The only configuration a step reads.
cross-project scope
ORCH_HOME/memory/ — spans projects, so it can belong to no repository.
A value is declared in exactly one scope. There is no merging and no overriding between scopes (AD-34). Mid-run edits to .orch/ never affect a live run, because the run reads only its snapshot (AD-9).

Deferred, and why each is safe

A deferral is safe only when no unit's interface depends on the answer. Each entry below names the decision that makes it so — that named decision is what you check before assuming the deferral still holds. Three remain, down from seven. 09

What the review changed

The spine went from 18 decisions to 34 after a four-lens Reviewer Gate — reconcile-spec, rubric, technology-verification and adversarial — which produced roughly sixty findings. The shape of the growth is the useful fact. In the same pass the deferrals went from seven to three, and the spec's open questions went to zero: the shadow-mode accuracy threshold is now provisionally set (over a rolling window of at least twenty shadow runs in one project, at least 80% produce a diff accepted without material change, and zero produce a write intent that would have been destructive — the destructive count being a hard gate, not a percentage), and the web renderer's stack is decided and pinned. ARCHITECTURE-SPINE.md is now an adopted companion of SPEC.md.

Nearly every addition was lateral, not vertical

A vertical decision picks one option over another: subprocess or SDK, TypeScript or Go, central or in-repo. Those were mostly right the first time. The adversarial lens confirmed AD-1, AD-10 (named the strongest decision in the document), AD-11, AD-13, AD-18, the AD-5 ignore-unknown-types rule and all six deferrals as closed.

A lateral decision fixes a contract between two units that both existed and both looked fine alone. Those were almost all missing. The command path between the renderers and the engine had never been named, so src/tui and src/web were literally unbuildable (AD-19). Containment had no decision at all, leaving CAP-10's own success criterion untestable (AD-20). The control/evidence split — identified in the source sessions as the highest-leverage architectural idea in the whole system — appeared nowhere (AD-23).

The lesson to carry forward: when you add a unit, the risk is not the decision inside it. It is the contract it shares with a unit someone else is building.

The three direct contradictions

AD-4 vs AD-7 — two named authorities

AD-4 called events.jsonl the durable truth while AD-7 called state.json the sole authority on progress. The web surface folds the log; the TUI morning brief reads the checkpoint. After every crash they diverge and both are "right". Fixed by ranking them: the checkpoint is a rebuildable projection of the log, and where they disagree the log wins.

AD-8 vs CAP-15 — the kill control undone

The kill control SIGTERMs a step. The reconciler then sees a recorded session id with no live process and helpfully resumes it. The safety control is silently reversed by the recovery loop. Fixed by recording a disposition on every step termination, where only interrupted is resumable and killed is never resumed or re-run.

AD-2 vs AD-17 — schemas in two places

AD-17 said an agent's TOML file declares its step contract schemas; AD-2 requires every schema to be a Zod schema in code. Both legal, mutually exclusive, and AD-17's claim that adding an agent needs no engine change was false as written. Fixed by making the TOML reference a registered contract id, never an inline schema.

Bonus: AD-13 + AD-4 composed into a leak

Neither was wrong alone. "Record every external request and response" composed with "events are never mutated" manufactures a permanent, un-redactable secret leak — the exact Critical threat in the threat model. Fixed by AD-21: redaction is a write-path invariant that fails closed, because there is no after-the-fact remedy.

Two blockers caught empirically

These were not reasoned about — they were reproduced. Both would have failed on the first real run, and both are now written into rule text rather than guidance, because guidance is what gets skipped.

T-1 · Zod 4 emits draft-2020-12; --json-schema requires draft-07
The spine mandated z.toJSONSchema() with no arguments. Zod 4 defaults to draft-2020-12, while the claude --json-schema validator is draft-07 and rejects it outright with no schema with key or ref https://json-schema.org/draft/2020-12/schema. The entire AD-2 step-contract chain — the mechanism by which every agent is a typed pure function — failed as written. The fix is z.toJSONSchema(schema, { target: "draft-7" }), and that argument is now part of the Rule, not a note beside it.
T-2 · npm 12 breaks npx github:
npm 12 disables git-dependency resolution and install scripts by default, and AD-12 makes npx github:<owner>/<repo> init the only supported onboarding path. The original stack pin of "npm 12.x" was wrong on two further counts: the dev machine ran 11.4.2, and neither recommended Node ships npm 12. The decision taken was to keep npx-from-git and document the hazard as a stated revisit condition rather than redesign distribution now — with npm pinned below 12 so no unit may assume the newer behaviour.

Dimensions that were silent

Findings of the form "this is not wrong, it is simply absent". Each became a decision.

  • Command transport — no path from renderer into engine was ever named → AD-19. The Deferred entry on the web renderer had justified itself by citing AD-3, which was circular.
  • Containment — the threat model specified hardened run flags, worktree-only mounts, no docker socket, two-phase network and an egress proxy; the spine fixed only image provenance → AD-20.
  • Control vs evidence plane — never appeared, despite being the highest-leverage idea in the source sessions → AD-23.
  • Ceilings — the three dimensions, hibernation and 80% degradation had no decision and no event types → AD-24.
  • The question envelope — CAP-1 through CAP-4 were governed only by a prose pointer → AD-25.
  • Re-run safety for git effects — AD-15 fenced only external writes; nothing said whether a re-run resets the worktree → AD-26.
  • The system's own tests — wholly silent, despite maintenance burden being the named top risk → AD-31.
  • One-writer enforcement — asserted everywhere, mechanised nowhere → AD-29 and AD-30.
  • Schema versioning and migration — an engine meeting an older .orch/ was undefined behaviour → AD-28.
  • Failure dispositions — retry, backoff and the repeated-failure handoff threshold were unspecified → AD-35.
AD-6 was retired. It deferred the SQLite query index — but its Prevents was premature-work avoidance rather than a divergence between two units, its "acceptably" clause was unenforceable, and it was duplicated verbatim under Deferred. A deferral wearing an AD's clothes. It now lives only in the Deferred list, where it belongs.
